## Order of operations

1. M0 ([`2026-10-29-dos-me-m0-seed-rekey.sql`](./2026-10-29-dos-me-m0-seed-rekey.sql)), then the seed change.
2. M1+M2 ([`2026-10-28-dos-me-m1-m2-items.sql`](./2026-10-28-dos-me-m1-m2-items.sql)).
3. **Item RPCs** (this proposal), whenever the web's Item catalogue (#1155, #1275) should stop grouping variants in the web.
4. The **compatibility window** (below).
5. **M3**, verify (V1, V5, V6, V7), then **M4**, verify (V2, V3, V4) and the M1+M2 verification file.

## Compatibility window: conditions before M3/M4

- `RATE_ITEM_MODEL` is on for the importer and the web, and has run for at least one promote cycle.
- Rate Services ships Item-aware code (design task 13): its auditors treat `cluster_id IS NULL` as "no variant", its refreshes are keyed by listing and Item, and its payloads carry `item_id`. M3 creates such listings in bulk.
- The M1+M2 verification file returns 0 on every expect-0 check (the reconciliation after the last writer changed).
- No listing without an Item (`SELECT count(*) FROM rate.products WHERE item_id IS NULL` = 0): M4 aborts otherwise.
- The sitemap has been re-crawled with Item URLs (about 30 days, design section 7).
- Active price alerts on `unknown` variants of multi-size Items (V7 before M3) are decided: an alert needs a size, so each is moved to a sized variant or closed. M3 aborts while one is active.
- The importer and the Rate Services writers are **paused** for M3 and for each rollback: M3 retires and backs up in one transaction, and a listing written in between would not be in the backup.

## What the files do

**Item RPCs** (SECURITY INVOKER except autocomplete, which is DEFINER like v1 because anon has no USAGE on the pg_trgm schema; all read published Items and published variants only; EXECUTE for `anon`, `authenticated`, `service_role`, `rate_worker`):

- `search_items_v1(...)`: one row per published Item with at least one published variant matching the filters. Same filter names as `search_master_products` where they apply; `p_storage_gb` means "has a variant of that size"; `p_has_5g` filters variants; `p_search` reads the Item and its published variants (name, key, chip); price filters and sorts use `matching_min_price` (cheapest priced matching variant). Returns the Item card fields and ratings (`user_rating_weighted`, `expert_rating`, `average_rating`, review counts), `matching_min_price` / `matching_max_price`, the representative variant (`representative_variant_id` and `_slug`: the cheapest priced matching variant, else the first matching one, so the card links to the size the filter asked for), `chips` (one JSON object per published variant: `variant_id`, `variant_key`, `slug`, `storage_gb`, `min_price`, `matching`), `variant_keys`, `matching_variant_keys`, `default_variant_id` and `total_count` for paging. Limit capped at 200.
- `get_category_brand_facets_v2(p_category_id)`: brands counted by published Item.
- `search_catalog_autocomplete_v2(p_query, p_limit)`: v1's result shape with `entity_kind = 'item'`.

**M3:** aborts if an earbuds master still has a sized key (apply M0 first) or an active price alert sits on an `unknown` variant it would retire. Then, for every Item with a live sized variant (never earbuds) and a live `unknown` variant (a NULL status counts as live), calls `rate.retire_item_unknown_variant` (M2): the listings keep their Item with `cluster_id = NULL`, the variant is archived, stats refresh. It then backs up the variant and exactly the listings the RPC marked (`metadata.retired_unknown_variant`) into `rate.m3_unknown_variant_backup` (RLS on, service role only). Single-variant Items are untouched.

**M4**, two transactions: (1) aborts unless every variant and listing has an Item; then `master_products.item_id NOT NULL`, `products_item_id_not_null` added as a CHECK `NOT VALID`, the `products_variant_item_guard` trigger (a listing's variant belongs to its Item), `items.default_variant_id` filled where unset (cheapest priced published variant, else the first published, else the first live one) and the `master_products_fill_default_variant` trigger, which names a default for an Item that has none when a live variant is written; (2) `VALIDATE CONSTRAINT` on its own, which holds only SHARE UPDATE EXCLUSIVE, so the listings table stays readable and writable during the scan.

## Deviations from the design (decisions for JOY)

- **M4 keeps the M1 sync triggers.** The design drops them in M4. The importer still relies on `master_products_sync_item` to create a new Item when it seeds a master (the matcher's `itemIdOfMaster` reads the Item the trigger made), and the listing trigger also carries the hand-set-variant guard and the item-follows-variant rule. Dropping them waits until the importer inserts Items itself (a later step); the M4 guard is the backstop meanwhile.
- **No master-side guard on `item_id` changes.** The design adds a companion trigger rejecting a variant's Item change while it has listings; M1's `master_products_move_listings` already moves those listings in the same statement, and V3 checks the result.
- **The M1+M2 retire RPC now treats a NULL status as live** (`IS DISTINCT FROM 'archived'`), the same as M3; the M1+M2 proposal file is updated in this PR (still not applied).

## Rollback

- RPCs: drop the three functions (turn the web's Item catalogue off first).
- M3/M4 (writers paused): drops the fill trigger, the guard, the CHECK and the NOT NULL, then restores the retired variants' status and their listings from the backup table (only listings still without a variant, on the same Item, still carrying the retire marker for that variant; any other listing changed after M3 and is left alone, with a NOTICE giving the count), refreshes stats, and drops the backup table. `default_variant_id` stays (nullable data M1+M2 already allowed).
